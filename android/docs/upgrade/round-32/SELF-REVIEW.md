## 用户视角

**已修复**

1. 章节号不连续（1,2,3,50）时，「继续阅读」打开第 50 话，不再回退第 1 话。
2. 完整章节重译只完成部分时，保留原完整译文，提示可重试。
3. 同一 `import_hash` 不同 id 的备份合并到现有书，章节/进度/书签不再成孤儿。
4. 旧备份没有 `data/chapters.json` 时，在线书按 `episodes` 补齐占位章节。
5. 润色/单段重译后清缓存，再重译整章不会拼回旧段落。
6. 「已移出」+ 搜索无结果，清除筛选后仍停留在已移出。
7. 打开另一本书的预览时不再显示上一本的加书错误。

**仍然存在**

- 源站新增/重排章节不会自动同步到现有书。
- 本地旧备份的章节标题无法恢复（备份本身没有该字段）。
- `data/chapters.json` 上限 8MB；超大书库会忽略该文件，书与进度仍恢复。
- 无真机：恢复、进度、缓存路径未在设备上逐条复现。

## 设计师视角

**一致**

- 进度以真实章节 idx 为准，不用「近似章节」代替。
- 完整译文是资产，partial 只是候选；失败提示明确「已保留原完整译文」。
- 书的身份按文件/源/ slug 多键判断，避免同一本书出现两份。
- 旧备份也能看到目录骨架，在线书可继续下载。
- 缓存失效让「润色」的结果不会被下一次整章翻译悄悄回滚。
- 筛选、预览错误都只影响当前上下文。

**取舍**

- Partial 保护会阻止用户用部分结果替换完整译文；当前没有「强制替换」入口，保守优先。
- 旧备份合成占位章节可能一次插入很多行（上限 5000）；这是可浏览性与体积的权衡。
- id 匹配顺序 id → hash → source → slug；slug 最后，降低合错书的概率。

## 工程师视角

**做对了**

- `continueChapterIndex` 是纯函数，`ChapterListScreen`/ViewModel 共用，测试覆盖缺口。
- `TranslationService.commit` 在写文件前判断旧 `complete` + 新 `partial`，直接返回可重试失败。
- `ImportPlan.remapBookIds` 同步重写书、章节、状态、书签、章节元数据；
  `ImportCoordinator` 在 commit 前完成匹配，`storageDirOverrides` 用现有目录。
- 旧备份占位章节只在 `metadata` 为空、非本地书、`episodes>0` 时生成，
  不干扰新备份和本地书。
- `TranslationStore.invalidate` 默认空实现，Fake 不受影响；只删目标章缓存。
- 清除筛选只调用有值的 setter；`preview()` 清空 `previewError`。

**风险与限制**

- `remapBookIds` 如果按 slug 误匹配，可能把备份数据合并到另一本书；
  当前顺序已尽量降低风险，但没有人工确认 UI。
- `storageDirOverrides` 只改写入位置，旧目录里的历史文件不迁移。
- 占位章节没有正文，打开时会触发下载；离线状态下会显示缺正文。
- 缓存失效是整章级别，润色后所有段落缓存都删，下一次重译成本更高。

**未验证**

- 真机上的备份恢复与继续阅读。
- 部分重译失败的实际 API 返回（测试未覆盖完整链路）。
- 大量章节（数千）恢复时的耗时与列表性能。

## 结论

Round 32 的 7 类修复落地，测试与 lint 通过。数据恢复从「书/进度/书签/章节」
扩展到「身份合并、旧备份目录、部分重译保护」；剩余问题集中在源站目录同步
与真机验证，属于 P2/P3，不再影响核心数据完整性。
