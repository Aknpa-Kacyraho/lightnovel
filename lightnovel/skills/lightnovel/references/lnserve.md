### 界面分页 + 书库（lnrecs.py）

需求原话：「推荐和收藏在同一界面会拥挤，有其他界面吗？」
「你爬过的书可以留下来进入书库，万一我以后又想看了去哪找？」

三个独立面板，hash 路由（`#recs` / `#shelf` / `#lib`），纯前端切换：

* **🎯 推荐** —— 按画像打分，显示命中理由 + 「＋ 加入书架」
* **📚 书架** —— 四堆（收藏/在读/看完/放弃）+ 更新提示 + 搜索
* **🗂 书库** —— **凡是爬过的书都留档**（`data/library.json`），
  可搜索、可标「★ 想看」、可「✕ 隐藏」、可随时「加入书架」

书库要点：

* `merge_into_library()` 按作品 id 去重、标签取**并集**、会变的字段
  （话数/评价点/更新时间）更新、记录 `first_seen` 与多个 `sources`
* `library_items(query, want_only, include_hidden)` 默认**不返回隐藏项**
* 想看与隐藏**互斥**（标想看会取消隐藏，反之亦然）
* 书库操作（q / want）走 `/api/library?q=&want=`，而 `/api/library` 无参数时
  仍返回**书架** JSON（前端定时刷新用）——改动时别把这两个语义搞混

### 推荐位（lnrecs.py）

`lnfinder`（找书那半边）的推荐能力通过 `lnrecs.py` 接到书架上，**别再让它只有命令行**：

* 书架最上方是「🎯 推荐给你」，显示日文标题 + 标签 + **命中理由** + 「＋ 加入书架」
* 结果缓存到 `data/recs.json`（TTL 12 小时）——
  **不要每次请求都去抓源站**，否则打开书架就打十几次上游
* 已在书架的作品显示「✓ 已在书架」，不重复添加
* `POST /api/add` 会复用 `lt.cmd_init`，并按 `source_id` 去重
* 复用画像与打分器（`taste_profile.json`），**不重写推荐逻辑**
* CLI 也能手动刷：`python3 lnrecs.py --top 60`

#### 「换一批」和「重新抓取」是两件事（报过"点了换一批没用"）

现象原话："为什么点了换一批没用。等了很久网页不刷新。"
查出来是**两个 bug 叠在一起**，都很典型，别改回去：

1. **语义错了**：按钮叫「换一批（重新抓取）」，实现是"用同一组关键词再打一次源站"。
   实测：同样的 20 个关键词重抓一次，拿回的 12 本**和分数一字不差**
   （25.5 / 25.2 / 24.8 / 24.1 …，顺序都一样）。所以等了 1 分 53 秒，
   刷新后看到的是**一模一样的页面**。**"换"永远不能靠"重抓"实现** ——
   源站是确定性的：同样的查询 → 同样的排序。
2. **慢操作同步等**：抓取是一个同步 HTTP 请求，全程零反馈，
   文案还写着"约 1 分钟"（实测 1 分 53 秒 = 20 词 × 约 5.7 秒）。
   读者视角就是"网页死了"。

现在的分工：

| 按钮 | 干什么 | 耗时 | 会不会打源站 |
| --- | --- | --- | --- |
| `⟳ 换一批`（`recs.rotate`） | 本地换页，游标存在 `recs.json` 的 `cursor` | **0.3 秒** | 不打 |
| `⤓ 重新抓取源站`（`recs.refresh_async`） | 真去源站搜，后台线程 + `x/y` 进度 | 约 2 分钟 | 打 |
| `⟳ 用书库里的（秒回）`（`recs.topup`） | 只给**书库存量**重排，空缓存时用 | 0.3 秒 | 不打 |

实现要点（踩过的坑都在这里）：

* `RECS_STORE = 60`：**存 60 本只显示 12 本**，就是为了让「换一批」有 5 屏料。
  只存 12 本的话"换一批"必然原地打转。
* `rotate()` 用 **id 游标**不是下标：隐藏一本会让所有下标错位。
* 翻页必须**按页对齐**（`_next_page`）：`(start+step)%total` 在总数不能整除时
  会滑出页边界 → 两屏重叠 6 本，且永远回不到开头。
* 补货换了榜单时（`total <= n` → `topup()`），用 `_least_overlap_page()`
  挑和"刚才那屏"重叠最少的一屏。否则新榜单第一屏还是旧那 12 本
  （同一套打分），看到的还是"换了怎么还有它"。
* `topup()` **不更新 `at`**：freshness 只描述"上次打源站是什么时候"。
  顺手更新会让「缓存较旧」这个 badge 永远不出现 = 骗人。
* `rank_library()` 把书库条目还原成打分器形状时**必须映射字段名**
  （书库 `points`/`updated` → 打分器 `review_points`/`last_episode_at`）。
  映射错了**不报错**，只是每本都判"评价点不足"→ 静默返回空表 ——
  看起来像"书库没有合适的书"，其实是名字没对上。
* 隐藏（「不感兴趣」）在补货路径也要生效：`rank_library()` 跳过 `hidden`。
* 抓取状态 `SCAN` 要在**起线程之前**同步写好，否则接口先返回 `0/0`
  且"已经在跑"的判据一瞬间不成立 → 连点两下会真的抓两遍（花两遍时间）。
* `scan_q_note()` 的耗时说明**按实测算**（词数 × 5.7 秒），别再手写"约 1 分钟"。

回归测试：`lntrans/test_recs.py`（21 项离线 + 14 项在线），
核心断言是"换一批之后那一屏和刚才那屏**零重复**"、
"轮完一圈每本书恰好出现一次"、"换一批不刷新 at"。

### 书架服务（首选交付方式）

**别再用"生成文件发给读者"的方式交付**。读者要的是「点开就读」：

```bash
cd <工具目录>/lntrans
python3 lnserve.py --port 8099          # 只在本机
python3 lnserve.py --port 8099 --lan    # 同时开给局域网（手机热点 → 平板）
# 浏览器打开 http://127.0.0.1:8099/
```

* **服务是前台进程，会话一结束就死**。下次要读之前**重新起一遍**，
  并 `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8099/` 确认返回 `200`
  （别只看进程在不在）。
* 浏览器和服务同机时 `127.0.0.1:8099` 直接可用；不同机才需要 `--lan`。
* `--lan` 会绑 `0.0.0.0`。**要输的地址以页面底部「📱 平板/其他设备访问」那行为准**
  （`/api/net` 现查，因为热点开关一次网卡和 IP 都会变；启动时算好写死就会过期）。
* `--lan` 下**需要表单登录**：启动日志给地址和口令，网址本身不含口令。平板打开后
  输入一次；成功时种随机 HttpOnly 会话 Cookie，**并另发一枚长期设备凭据**
  （不是主口令；`data/devices.json` 只存 sha256，默认 180 天、用一次续一次）——
  服务重启、浏览器重开都不用再输，设置页「退出本设备」才撤销。
  回环地址免登录。可用 `LNTRANS_TOKEN` / `LNTRANS_TOKEN_FILE` 固定口令，
  `LNTRANS_DEVICE_DAYS` 调记忆时长。

#### 本地导入与术语过期提示（2026-10-22）

* `/import`：选 EPUB/TXT + 可选书名/作者，文件以**原始 body** `POST /api/import`
  （上限 32MB，不 base64）；解析交给 `lnimport.py`，建书后自动放进书架「想读」。
  成功页给章数、书名和 `/read/<slug>` 链接。EPUB 解析的硬规矩：剥掉 ruby 的
  `rt`/`rp`、manifest `href` 去掉 `#锚点`/`?query`、TXT 第一个标题前的短前言
  不能丢、无空行 TXT 按一行一段重排。
* **术语过期**：阅读页只检查本页渲染的 1~2 章（`chapter_glossary_stale`），
  命中就渲染 `.stale-note` + `data-stale-retranslate=N`；按钮发
  `/api/translate {force:1, after:N, count:1, ceiling:N}` 后轮询 `/api/job`，
  成功用 `/api/chapter?ch=N` 就地替换并移除提示。有任务在跑时 force 返回 409
  （不能把旧任务当成排队成功）。
* 导入/过期相关的按钮必须在 `test_click` 里真点：`/import` 页的 `imp-go` 要有
  handler；`__stale_seed__` 种子书要能渲染提示并发出 force 请求。
  `test_pages` 还要覆盖真实的 `/api/import` 上传落地（成功后清理测试书）。

三个坑（都是实测出来的，别照直觉写）：

* 不要指望 `ip` / `ss` / `netstat` / `/proc/net`（受限环境里没有或被拒）——
  用 `socket.if_nameindex()` + `SIOCGIFADDR` ioctl（`lan_ipv4()`，纯标准库）。
* 手机**自己连的路由 Wi-Fi 那张网卡，平板是够不着的**，平板只能走热点那张网卡。
* ❗**别靠网卡名猜哪张是热点**。第一版按「名字像 `ap*`/`wlan1`、或者地址以 `.1` 结尾」
  打 ★ —— 在真机上**全猜错**：热点网卡既不叫那几个名字、地址也不以 `.1` 结尾，
  于是页面把真正的地址排在后面还不打 ★，用户只能在平板上一个个试。
  真正的判据是**实测**：`_is_tethering_addr()` 去连 `<ip>:53` ——
  **只有热点接口上才会有本地监听的 53 端口**（netd/dnsmasq 给连上来的设备解析 DNS），
  手机自己连的 Wi-Fi 不会在本地开 53。连不上一般立刻 ConnectionRefused，
  常态下没有额外耗时（结果缓存 15 秒）。名字启发式留着当兜底，两者取或。

**"平板到底连上了没"这件事，服务端本来完全看不见** —— 只能靠用户反复试地址。
所以顺手记了一张最近来访的**外部设备**表（`PEERS`，只存 ip + 时间，回环不算，
上限 20 条），`/api/net` 里以 `peers` 返回，页面底部显示"已经连上过的设备：…"。
调试时它的用处很大：用「热点地址」打开一次页面，就能反过来证明
"绑定 0.0.0.0 + 这个地址"这条路真的通（回环打开**不会**被登记，正好做对照）。
* 有口令：绑非回环地址时要求表单登录（`LNTRANS_TOKEN` 或 `LNTRANS_TOKEN_FILE`，
  都没有则启动时随机生成）；回环地址免登录。写请求校验 Host 与同源 Origin，
  登录/翻译启动限速，响应带 CSP、frame、Referrer 和 nosniff 等安全头。

#### 翻译调度（v5.1：在读就一直翻）

* **不再有「自动翻译开关 / 读到 + N 章」**。`lnsched.py` 是唯一决策点：
  读者打开书、翻页、轮询都会刷新 `last_read_at`；在 `idle_minutes`（默认 30）
  之内，调度器持续翻这本书的下一章，没有上限；超时自动停。
* **翻译列表** `/queue`：把书加进来按顺序提前翻，可上移/下移/暂停/移出；
  全局每日 token 预算（默认 30 万，**仅提醒**，0 = 不限）与全局暂停也在这里。
* 停止 = 暂停本书（`paused`），只有显式「继续」或手动翻译才解除；
  重启中断的任务会自动续跑（见上），两者不要混。
* 策略与 IO 分离：`lnsched.py` 不碰章节/模型，只维护 `data/sched.json`，
  所以能用纯单元测试钉住；`lnserve.py` 的 dispatcher 只负责"问调度器要书 → start_job"。

#### 它做了什么（这是"读到哪翻到哪"的落地）

* `/` 书架：所有作品卡片，显示中文书名、`已译/总章`、进度条、收藏状态
* `/read/<slug>` 阅读页：中文正文 + 日文对照（默认折叠）+ 目录 + 进度条
* **滚动到接近底部自动续译**：前端 `POST /api/translate` → 后台 worker 翻译
  → 轮询 `/api/job` → `GET /api/next` 把新章节**追加到页面**，不用刷新
* **「已译章节」是完整目录**：列**全部**已译章（不只本页那几章），中文章节名 +
  日文小字副标题；本页内的章走锚点、本页外的走 `/read/<slug>?from=N`，点一下就过去。
  副标题只在"中日不同"时才显示。
* **章节名会被自动翻成中文**：worker 每次动手前先 `ensure_zh_titles()`
  （一次请求翻完书名 + 已读到范围里的章节名）。不做的话目录和大标题永远是日文
  —— 需求原话：「你汉化完了显示汉化章节，我点进去来看，这样清晰明了」。
* ⚠ **落地章没译文时不许偷偷跳到下一章**：渲染 `#need-N` 占位块（"这一章还没译好，
  译好会自动出现在这里"），并置 `window.__NEED__`；一进页面就去翻它，
  译好后用 `GET /api/chapter` **就地替换**占位块（不重新加载、不动阅读位置）。
  需求原话：「我还没开始看，怎么就第二话了，我第一话呢？」「自动翻译完成某章后
  怎么不刷新，我还要手动刷新？」。`GET /api/next` 遇到空洞也**不跳过**，
  返回 `need=N` 让前端等这一章（否则读者会从第 3 章直接看到第 5 章）。
* **「已译 N 章」= 真有译文的章数**（`have_count()`），不是"从第 1 章起的连续前缀"
  （`translated_count()`）。用错会显示「已译 0 章」而下面明明列着 6 章。
* **翻章要落在正文**：链接带 `?from=N#cN` 锚点；目录默认折叠（`<details id="tocbox">`）。
* **导出 EPUB**（`lnepub.py`，阅读页「下载 EPUB」）：只放译文、只收已译章；`mimetype`
  必须是第一个条目且 STORED（OCF 规范，压缩了部分阅读器直接拒收）；OPF 里的 `item id`
  必须是 NCName（**不能**用 `text/ch0001.xhtml` 这种路径），否则 spine 找不到它、
  整本书在阅读器里空白 —— 这类错不抛异常，只有结构测试抓得到。
* **详情页作品横幅**（`lncovers.py` + `/cover/<key>`）：源站 `og:image` 是 1200×630 的
  宣传图（大字标题 + 简介），**不是插画封面**；所以只放详情页当横向横幅，不塞进卡片
  的竖版缩略框。抓取进后台单线程队列（限速、去重），渲染路径只读本地文件。
* **「前情 · 人物」面板**（`memory_panel`）：把 `summaries` / `characters` / `glossary`
  搬到阅读页 —— 这三样原来只喂翻译 prompt，读者看不见。隔周回来点开第 37 章，
  先看"上次讲到哪 + 这几个人是谁"。**只用第 1 章到当前章 -1 的章节**（后文才出场的
  人物/术语不出现，不剧透）；没有梗概时兜底显示上一章结尾，并明说"还没有提要句"。
  梗概用 `python3 lntrans.py summary <slug> --from-chapter N --count 2` 生成
  （实测约 1.3k~3k token/章）。
* **正文里的术语/人名可点**（`lnrender.annotate_terms`）：只标**中文译名**
  （读者不读日文），点一下弹气泡显示原文与人物简介。单字译名每章最多 3 处、
  每章标注上限 60 处 —— 标太密正文就没法读了。气泡 `#gtip` 只由 `reader.js` 创建。
* **底部条 = 一套状态 + 一条进度**：`#tb-status`（只有章号会变）+ `#tb-prog`（`已译 x/y（p%）`）
  + `#tb-fill`（顶部细进度条）。别让 tick/poll 各写一套文案，否则会闪。
* **预翻下一章**：`__NEXTTRANS__`=下一章已有译文；`__NEXTHAVE__`=链接可点（恒真）。
  落地章有译文就立刻 `tick()` 预翻下一章，读起来才不像"每章都要等"。
* **章末导航**（`.chapnav`，上一章 / 目录 / 下一章）：读到章末不必滚回顶部找目录。
  缺译章那一页**不许给「下一章」链接** —— 那会落到又一个占位页，而它的 `tick()`
  用 `after=need+1` 排翻译，正在等的那一章被跳过、可能永久缺译；下一章真有译文
  才给链接（正当的"绕开空洞"出口）。
* **连续阅读**：阅读页支持 ← → / `j` `k` / 左右滑动翻章；滑动起点在反馈浮层、悬浮按钮、
  输入框上时不触发（那是用户在操作，不是翻章）。批边界处整页跳 `?from=N`。
* **进度上报**：`IntersectionObserver` 检测视野中的章节，`POST /api/progress`。
  所以"读者读到第几章"是服务端已知的，也只翻他附近的内容
* **收藏** `POST /api/favorite`、**反馈** `POST /api/feedback`（带章节号+留言）

#### 四类书堆与"什么信号才值得学"（需求原话驱动的规则）

需求原话：**「我看的不代表我喜欢，可能我只看一点点就放弃了」**
——所以**只有收藏**能作为正向信号进画像。

| 书堆 | 判定 | 查更新 | 学画像 |
|---|---|---|---|
| ★ 收藏 `favorite` | 主动点收藏 | ✅ 永远查 | ✅ **只有它** |
| 在读 `reading` | 有阅读记录且近期活跃 | ✅ 查 | ❌ 不算喜欢 |
| ✓ 看完 `finished` | 手动标记，或读到最后一章 | ❌ | ❌ |
| ✗ 放弃 `dropped` | 手动标记 | ❌ | ❌ |

附加规则：
* **搁置 ≠ 放弃**：很久没打开的书仍留在「在读」，只标「搁置 N 天」。
  **绝不能自动挪进放弃堆**（读者会找不到书，而且会平白停掉更新检查）。
* **休眠**（`is_dormant`，默认 60 天）：没收藏 + 超 60 天没打开 → 不自动查更新
  （原话："我没看的你就不要浪费 token"），**一旦再打开自动恢复**。
* 函数分工：`book_status()` / `should_watch()` / `should_learn()` /
  `watch_list()`。测试要调 `watch_list()` 本身，**别在测试里重拼一遍逻辑**——
  这么干过，漏传 slug 参数，于是休眠规则没被验证到，白跑一轮。

#### 更新检查：**打开某本书时才查**（默认，别改回去）

需求原话：「改成我打开这本小说，你才检查更新，这样更加方便省 token」。
所以默认**没有**定时轮询：

* 打开 `/read/<slug>` → `check_on_open(slug)` 查这一本；
* **不打开 → 零请求**（自检验证：渲染书架 + 算 watch_list，源站调用次数 = 0）；
* **6 小时内重复打开不重复查**（`CHECK_MIN_INTERVAL_H`），
  实测第一次打开 2651ms、第二次 129ms；
* 只拉**作品页章节列表**（`lt.fetch_work`），**不花翻译 token**；
* 记录 `episodes_latest` / `last_episode_at` / `checked_at`；
  比上次多话或最新话时间变新 → `has_update` + `new_episodes`；
* 书架顶部弹「有 N 本更新了」，卡片打红色「更新了 +N 话」徽标；
* **发现更新不自动翻译**——只打标记。读者往下滚时按需翻。

想改成主动推送，用 `--watch --every-hours 12` 显式开启（`update_daemon()`）。

两个必须记住的实现细节：

1. **首次检查只建立基线**，不会报"更新"——没有历史就无从比较。
   自检里验证 delta 必须**先建基线再改变话数**，否则会误判成 bug
   （第一次就写错了这个测试）。
2. `/api/check` 单本走 `check_on_open(force=True)` 绕过去重；
   书架上的「⟳ 全部查更新」才会遍历 `watch_list()`。

#### 用户状态文件（下一次对话要读它）

**按书拆分**在 `data/books/<slug>.json`（旧版是单文件 `data/user.json`，
`load_state()` 会自动迁移一次，迁移后原文件改名为 `user.json.migrated`）：

```json
{
  "progress": {"<slug>": {"chapter": 6, "at": "..."}},   // 读到哪
  "favorites": {"<slug>": "..."},                        // 收藏
  "feedback": [{"slug","chapter","vote","note","at"}]     // 逐条反馈
}
```

**接到反馈/要调整画像时，先读这个文件**，再决定 `learn` / `fix`。
`vote` 有 `good`/`bad`/`trans`，`note` 是读者原话，信息量最大。

#### 章节正文里混进网站页脚（历史数据）

抓正文的 fallback 一度是"从 `widget-episodeBody` 起切 200KB 再正则抓 `<p>`"，
把阅读器设置面板、応援コメント、注册引导全当正文抓了进来，LLM 又把这些翻成中文
—— 每章末尾都能读到「点击滚动 / 部分安卓设备上字体设置不会生效」。
现在抓取只取 `widget-episodeBody` 那**一个 div**（按标签深度扫到配对的 `</div>`）。

已经落盘的脏数据用 `repair_chrome.py` 清：

```bash
cd <工具目录>/lntrans
python3 repair_chrome.py                       # 干跑，只报告
python3 repair_chrome.py --slug <slug> --apply # 真改（先备份到 /tmp）
```

它的规则是**保守**的：重新抓一次干净原文（免费、不花 token）→ 与旧原文按段求
共同前缀 → 旧文件前缀之外的当残留删掉 → 译文**同索引一起删**（渲染是
`zh[i] ↔ jp[i]` 逐段对应的，只删一边会让中日文错位）；段数对不上就先单独找译文侧
的页脚锚点交叉验证，仍然对不上就**跳过并报告**，绝不猜。
判据：`test_reader.py` + 跑完自己再跑一次应报"干净"（幂等）。

#### 性能与并发（都是实测出来才写的）

* **卡片渲染不许"每张卡扫一遍全表"**。`work_head()` / `work_status_chips()` 每渲染
  一张卡都要"这书的中文名 / 我在不在读"，如果那里 `listdir` + 逐个读 `meta.json`，
  一个书库页（300+ 张卡）就是几万次文件读 —— 实测首页 **5.0 秒**。
  现在：`_slug_index()`（source_id → slug 反查表，按 novels 目录 mtime 缓存）
  + `novel_meta()` 的 (mtime,size) 缓存，同一个页面 **0.5 秒**。
* **打开阅读页的更新检查必须限时**：实测一次源站查询 3.1 秒，同步等就是"页面卡住、
  要自己刷新"。`check_on_open_bounded(slug, timeout=1.0)` 把它丢后台线程，
  查得快就顺手标"更新了 +N 话"，查得慢页面立刻出来。
* **worker 里所有可能调 LLM/抓站的步骤都要 `except (Exception, SystemExit)`**：
  `die()` 走的是 `sys.exit()`，只 `except Exception` **接不住** → 线程直接死掉，
  之后所有翻译任务永远卡在 running（缺 key 时就是这样，整条队列瘫痪）。
* **后台任务要能认出"我还是当前任务吗"**（`JOBS[slug]["token"]`）：心跳超时只标成
  `interrupted`，不会伪装成仍在运行；用户确认恢复后才建新任务，旧任务必须自己停手，
  否则同一章被翻两遍（重复花钱）。
* **任务状态必须持久化**：每个任务在 `data/jobs/<job-id>.json`；进程重启把遗留
  `queued/running` 改成 `interrupted`。完成章节由正文 + `chapters/NNNN.meta.json`
  重新计算，不重放队列。任务日志损坏时进入受限恢复模式：阅读、进度、书架和
  备份仍可用；开始/停止翻译等任务写入返回 503，绝不自动清空坏日志。
* **「停止翻译」= 停任务 + 关自动翻译，排队项必须带 token**：`cancel_job(slug, disable)`
  换 token 并 `set_trans_cfg(enabled=False)`；`JOBS_Q` 入队带 token，worker 出队先比对，
  不一致/已 cancelled 的直接丢弃 —— 否则"刚入队就停"会被 worker 翻回 running，等于没停。
  前端 `#tb-stop` 只在 running/queued 时显示；点停止与轮询到 `cancelled`（别的设备停的）
  都走同一个「已停止 · 继续」渲染，别只写一行状态、把用户逼去刷新。
* **失败痕迹要持久化、且成对清除**：失败时 `update_book` 写 `trans_error/trans_error_at`
  （卡片读 item，零 I/O，重启后仍能显示「翻译失败 / 重试」）；**真译到了东西**的成功结束
  才清除（「未开启翻译」这类空跑也走 done，不能顺手抹掉上次的失败徽标）。
  注意 `update_book` 用的是同一把 `LOCK` —— 持锁调用会自锁死，必须在锁外写。
* **章内进度报「第 N 章 · 段 x/y」**：`translate_chapter(..., progress=cb)` 在分段循环顶部回调，
  worker 写 `JOBS.message`；长章十几段，只写"正在翻译第 N 章"会像卡死。回调内异常要吞掉。
* **`/api/job` 不许刷新心跳**：心跳要反映 worker 真实存活；前端每 2.5 秒轮询一次，
  轮询也刷心跳的话"卡死兜底"永远不触发。
* **原文/译文一律原子写**（`save_text()`：先 `.tmp` 再 `os.replace`），
  否则进程被杀留下半截文件，而 `has_translation()` 只看 `size>0` →
  截断内容被**永久当成"已译"**跳过。
* **翻译失败绝不落盘/不缓存/不算已译**：写 `progress.incomplete` 记账，
  `--allow-missing` 写出也要标 `incomplete`（目录里显示「未译全」）。
  让原文冒充译文是最坏的结果 —— 一旦落盘就会被永久复用。

#### 服务端踩过的坑（都是自检抓出来的，别改回去）

1. **worker 必须自己抓原文**：CLI 的 `next` 自带抓取，worker 直接调
   `translate_chapter` 会 `FileNotFoundError`。已抽出 `ensure_raw()` 两边共用。
2. **重启服务不要用 `pkill -f lnserve.py`**：它会把**自己所在的 shell** 一起杀掉
   （命令行里含同样的字符串）。用后台任务的 job id 去停，
   或者按精确 argv 匹配（`/proc/<pid>/cmdline` 里 `argv[1]` 以 `/lnserve.py` 结尾）。
3. **空洞容忍**：不能"遇到第一个空洞就 break"。`translated_count()` 现在只表示
   *连续前缀*（给"下一页从哪取"用），判断"哪些已译"必须用 `zh_chapters()`，
   选"该翻哪几章"必须用 `next_targets()`（优先补空洞）。
   老实现下「1,2 译好、3 失败、4~8 译好」会让后面 6 章**直接不可见**并重翻。
4. **反馈写入必须用 `append_feedback()`**，绝不能用 `save_state(整份聚合状态)`——
   聚合状态里含所有书的历史反馈，整体写回会把它们**重复追加**
   （自检抓到同一条被写了 4 次）。`set_progress()`/`toggle_favorite()`/`set_opened()`
   同理，都是针对性写入。`save_state()` 只保留给兼容用途。
5. **自检脚本必须按生成规则清理**：造了 `bookNNN` 却只删 `__selftest__`，
   结果 20 本假书留在书架上（显示"在读 20 本"）。清理要用 `purge_fake_books()`
   按实际命名规则删，并且**自检跑完必须确认书架是干净的**。
6. **不要在代码里写死测试日期**：用固定的 `2026-09-01` 判断"超 60 天休眠"，
   过一阵就失效。要用 `time.time() - N*86400` 相对计算。
7. **反馈 UI 不能放在页尾**：自动续译会不停往下追加内容，页尾表单会被越推越远。
   现在是右下角常驻按钮（`#fab`）+ 浮层，自动带上"当前所在章"。
8. 模块加载时 `importlib` 注入 `lntrans`/`lnrender`，所以两者都要保持
   可安全导入（顶层不能有副作用）。

### 视觉呈现（不要只丢一个 md 文件给读者）

纯 Markdown 长篇阅读体验很差。必须渲染成阅读页面：

```bash
python3 lnrender.py <slug>              # 生成 novels/<slug>/read.html
python3 lnrender.py <slug> --theme light  # 写死主题（调试用）
```

页面特性：暖色纸感背景 / 衬线中文正文 / 章节目录 / 阅读进度条 /
**原文⇄译文对照（默认折叠日文）** / 深浅色跟系统 + 手动切换。
自包含单文件，无 CDN 依赖，离线可开。

**章节名必须翻成中文**，否则目录里全是「第1話　〈日文原标题〉」，
对不懂日语的读者毫无意义：

```bash
python3 lntrans.py titles <slug>    # 一次请求批量翻译，很便宜
python3 lnrender.py <slug>          # 重新渲染
```

#### 踩过的坑（改前端时注意）

1. **不要在 `body` 上显式写颜色再用 `prefers-color-scheme` 覆盖变量**——
   媒体查询只覆盖变量，赢不了 `body` 的显式声明，暗色令牌会泄漏到浅色主题。
   正确做法：主题令牌放 `html`，用 `html[data-t=dark]` 显式类切换。
2. **首屏主题要在 `<head>` 里定**（内联脚本 + `color-scheme` meta），
   否则会闪一下白屏，浏览器也可能自行反演配色。
3. **Edge/Android 的「强制深色网页」会把浅色反演成深棕**，
   连 `#ffffff` 都会变深灰。这是浏览器设置，不是页面 bug——
   用最小复现（纯 `#fff`/`#f00` 色块）就能确认。遇到反馈"颜色很怪"，
   先让他关掉浏览器的强制深色，或换成 ReadEra 等本地阅读器。
4. Python f-string 里嵌 JS 要注意花括号会被吃掉：用普通字符串拼接。

### ⚠ 前端 JS 语法错误 = 所有按钮失效（报过三次）

这是本项目**最高频、最难查**的一类 bug。特征：

* 服务端 API 全绿、`python -m py_compile` 也 OK
* 但浏览器**整段 `<script>` 解析失败** → 里面所有 `onclick` 都没绑上
* 表现是「点了没反应」，而且**不报错**（控制台之外无迹可寻）

已发生的三次：

| 原因 | 现象 |
|---|---|
| 卡片 `onclick` 里用单引号拼在双引号属性内 | 属性被截断，DOM 结构崩坏，按钮脱离 `.card` |
| 替换 handler 时把 `catch` 删掉 | `try{}` 悬空 → 整段脚本解析失败 |
| 替换时留下多余的 `try {` 没配 `catch` | 同上 |

**两层防线，缺一层就会被用户看出来**：

**第一层：语法**（`test_ui.py`）—— 把页面 `<script>` 抽出来交给 Node 的
`new Function()` 编译（等价浏览器解析，语法错立刻暴露）；断言 `try`/`catch` 配对、
每个动作前缀都被事件委托覆盖、不再逐个绑 `.ctrls button`。

> **前端脚本现在放在 `lntrans/static/*.js`**（ACTION / LIB / DISLIKE / READER / DETAIL /
> REVIEW；阅读页的日文折叠·主题·排版·常驻工具栏也在 READER），页面样式在
> `static/app.css`（`CSS = lnrender.CSS + _read_static("app.css")`），都由
> `lnserve._read_static()` 读入后**仍内联注入**（渲染不变）—— 不再内嵌在
> Python 字符串里，所以上面第 4 条"f-string 吃花括号 / 引号截断"的坑没有了。
> 改前端就改 `static/*.js`，并跑 `test_js_static.py`（存在非空 + 与模块变量一致 +
> `node --check`；`app.css` 缺失会让服务**起不来**，所以额外断言 CSS == 基础 CSS + 全文）；
> 别再写回 `.py`。

**第二层：行为**（`test_click.py` + `test_click_dom.js`）—— **只编译 JS 远远不够**。

两个必须遵守的细节（都是被外面的人审出来的）：

* DOM 桩里 `getElementById` 对**页面 HTML 里不存在的 id 必须返回 `null`**（和浏览器一致）。
  桩原来越界"友好"（任何 id 都返回一个稳定对象），于是
  `document.getElementById('btn-fav').onclick=...`（那个元素早就不存在了）
  在真实浏览器里抛 `Cannot set properties of null`，**整段脚本后续绑定全废**
  （日文折叠开关、主题按钮集体变死按钮），而桩里一路绿灯。
* 要断言**每一个带 id 的按钮都有 handler**（除非它走 `data-act` 事件委托），
  不能只抽查 `check-all` / `theme` 两个 id。上面那个 bug 就是抽查漏掉的。

"语法合法、行为错"正是"按钮点了没反应"最常见的成因，编译器一个都抓不到：

| 真实踩过的 bug | 语法层看得出吗 | 行为层看得出吗 |
|---|---|---|
| 详情页 ★收藏 的 `class` 写死 `on` → 前端永远发 `value:false`，收藏永远开不了 | ❌ | ✅ |
| 卡片上「更新了·点我翻译」不在 `.ctrls` 里 → 从来没人给它绑 handler | ❌ | ✅ |
| 一处 `getElementById(...).onclick` 抛异常 → 之后的绑定全部失效 | ❌ | ✅ |
| 属性引号未转义 / `catch` 被删 | ✅ | — |

`test_click_dom.js` 用**最小 DOM 桩**（`document` / `location` / `fetch` /
`setInterval` / `IntersectionObserver` … 加 `.closest()` / `dataset` / `classList`
的极简实现）把页面脚本**真的执行**一遍，再按 HTML 里每个按钮**真的点一次**，断言：

1. 脚本执行期间没抛异常；
2. 每个按钮点下去**发出的请求**正确（动作名、`value`、payload —— 尤其是
   "收藏按钮没点亮时必须发 `value=true`"）；
3. 按钮的 `on` 状态 == `/api/library` 返回的真实状态（**UI 必须等于实际**）；
4. 书架卡显示的书名 == 接口给的书名（顺手抓"没翻译 / 同一行日文显示两遍"）。

样本必须覆盖**两种取值**（已收藏 / 未收藏 各一本），否则一个"全写死 `on`"的
实现也能蒙混过关。并且要**验证测试本身有效**：故意删掉一个 `catch`、或去掉某个
`data-act` 的处理分支，确认测试会报错 —— 否则又是一个"永远通过的断言"。

改前端时的铁律：**每次改完都跑 `run_selftests.py`**。只跑 Python 语法检查没用。
`curl` 不执行 JS —— 拿 `curl` 验证 DOM/JS 行为，得到的结论一定是错的。

#### 按钮绑定：只准用**事件委托**，不许逐个 `.onclick=`

踩过三次「按钮按了没反应」，每次漏绑方式都不同（见上表）。现在全站只有一个
绑定点：`document.addEventListener('click', …)`，匹配
`[data-act] [data-d-act] [data-add] [data-d-add] [data-want] [data-gopage]`。
按钮放在哪、是不是动态插进来的、以后新加什么按钮，都自动可用。
**新增动作按钮 = 加一个 `data-*` 属性 + 在分发函数里加一个分支**，
不要在页面里再写 `getElementById(...).onclick=`（那正是上面第 3 类 bug 的来源；
真要写也必须先判空）。

### 状态机（先设计，再写代码）

**`STATE-MACHINE.md` 是本项目的状态权威文档**（四个 tracking 状态 + 收藏正交维度 +
完整转换表）。改状态相关逻辑前先读它。

需求原话：「确保 UI 显示和实际情况一样」「我居然放弃了的话就自动移除收藏和在看」
「你要思考这种小细节，不要让我每次反馈」。

关键规则：

* **收藏与 tracking 正交**：`favorites` 独立存储，与 want/reading/finished/dropped
  互不影响。「收藏+看完」是正常组合，卡片上显示**两个徽标**。
* **弃文自动清收藏**：`apply_action(slug,'dropped')` 会同时清掉 `favorites`，
  并在响应里带 `cleared_favorite`，前端提示「已弃文 · 已自动移出收藏」。
* **所有变更走唯一入口** `apply_action()`，不要在别处直接改字段。
* **`read_tracking()` 在"不在书架"时必须返回 `None`，不许伪造 `"want"`。**
  踩过：把"没有 tracking"和"想读"当成同一个值，于是「打开阅读页 → want 转 reading」
  这条规则对**已移出书架**的书也生效 —— 用户点「✕ 移出」后一打开书接着读，
  书又回到书架，连点三次都"没反应"。测试要断言"移出后打开阅读页不会被加回"。
* **「加入书架」≠ 收藏**（用户原话：「我加入书架不等于收藏，因为我（不加）看不了」）：
  `/api/add` 必须显式 `ensure_on_shelf()` —— 写 `tracking=want` 上架，
  **绝不碰 `favorites`**。踩过两个坑：`/api/add` 只建目录不写 tracking，
  于是"加进来了、书架里却没有"；而 `shelf_source_ids()`（推荐卡上那句
  「✓ 已在书架」）又用了另一套判定（只看目录在不在），两处不一致 → 用户彻底迷路。
  两条轴要在界面上**当场写清楚**：在不在书架 = 能不能读；★收藏 = 喜不喜欢（只学口味）。
* **UI 状态由服务端响应渲染**：`/api/status` 返回 `{favorite, tracking}`，
  前端 `applyCardState()` 据此点亮按钮/徽标 —— 这样 UI 必然等于实际。
* **中文书名有两个来源，必须合并读**：`novels/<slug>/meta.json` 的
  `zh_titles.book`（**章节翻译**写的）与 `data/details/<源id>.json` 的 `zh_title`
  （**列表页/详情页**翻译写的）。只读前者 → 同一本书在推荐卡上是中文、
  书架上是日文（用户报「书架里的书标题没翻译」）。补翻也要两处都排队：
  `/api/translate_meta` 按作品 id 翻，书架上的书要能被同一套批量任务覆盖到。
  日文原名只在中日不同时才显示第二行（否则大标题和小字是同一行日文，看着像坏了）。
* **书架分组必须覆盖所有 tracking 取值**。踩过：加了 `tracking="want"` 却忘了
  建这一堆 → 书从所有分组掉出去 → 书架显示「还是空的」，但 `library()` 有书，
  看到的却是「点了没反应」。现在加了兜底（`lost` 收集漏掉的，用来**暴露**分类漏洞，
  而不是把它们静默塞回某一堆）。
* **别用 `disabled` 长时间锁按钮**：MDN 明确 disabled 的按钮不触发 click。

### 前辈知识（`PRIOR-ART.md` 是权威记录）

需求原话：「能利用前辈们的知识是你最大的优势，不要闭门造车」。
**改设计前先读 `PRIOR-ART.md`**，里面记了从成熟项目读源码得到的结论与采纳理由。

已读并采纳 —— **auto-novel 自己的 translator**（`packages/translator/src/`）：

| 它怎么做 | 我们采纳成什么 |
|---|---|
| `detectChinese()` 校验译文语言 | `detect_chinese()`：**只校验行数不够**，模型会把日文抄回来 |
| 行数连续 3 次不符 → `binaryTranslate()` 拆半递归 | `robust_translate_paras()` 按段落二分（`depth<4`） |
| `Semaphore` 限制并发 | `_GLOBAL_SEM = Semaphore(3)` |
| `SegmentQueue` 高水位背压 | 思路记录（我们逐段串行，规模不需要队列） |

已读并采纳 —— **LightNovelReader**（★2242，中文轻小说阅读器，最贴近我们的场景）：

| 它怎么做 | 我们采纳成什么 |
|---|---|
| `currentChapterReadingProgressMap` / `maxChapterReadingProgressMap` **双轨进度** | `progress.scroll`（续读位置）+ `progress.max_scroll`（进度%）。**只存一个最远值是错的**：往回翻一点再退出，下次会被送到最远处 |
| `BookshelfSortType` 作为**可持久化设置** | 排序目前写死，是已知短板 |
| `updatedBookIds` 是书架里的**id 列表** | 我们是每本书的 `has_update` 布尔 |
| `BookshelfBookItem` **没有 status 字段** | 第三次印证：成熟阅读器围绕「内容+进度+更新」，不是状态标签 |

已读并采纳（Kavita ★11.8k，`github.com/Kareadita/Kavita`）：

| 它怎么做 | 我们采纳成什么 |
|---|---|
| `AppUserProgress.BookScrollId`（滚动锚点续读） | `progress.scroll` + 阅读页 `__SCROLL__` 恢复 |
| `AppUserWantToRead` 是**独立表**，不是状态枚举 | 印证：`tracking` 与 `favorites` 两个正交维度 |
| `AppUserReadingSession`（起止时间、活动数据） | `data/history.jsonl` + 书架「连续阅读天数」统计 |

**最有价值的一课**：主流阅读服务器（Kavita / calibre-web / Komga）都用
**「进度（事实）+ 列表/收藏（意图）」**两个维度，**没有**让用户维护一个状态机。
我们本轮把这一点对齐了。

没采纳的也记了原因（`TotalReads` 重看次数、分页 `PagesRead` 等），
避免以后反复纠结同一件事。
