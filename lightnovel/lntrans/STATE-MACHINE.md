# 书库状态机（先把细节想清楚，再写代码）

> 用户批评：「你要思考这种小细节，不要让我每次反馈」。
> 所以这份文档的用途是**穷举所有状态与转换**，避免再靠用户试出来。
> 参考的业界惯例：Goodreads / Open Library 的 Want to Read · Currently Reading · Read
> 三分法，加上中文网文圈通用的「弃文」；豆瓣/起点也都有「养肥/弃文」。

---

## 一、四个状态（互斥，非并列）

| 状态 | 含义 | 会不会自动查更新 | 会不会进画像 |
|---|---|---|---|
| `want` 想读 | 加了书架还没开始看 | 查 | 不进 |
| `reading` 在读 | 开始看了 | 查 | 不进（用户原话：看的不代表喜欢） |
| `finished` 看完 | 读完了 | 查（可能出番外/续篇） | 进 |
| `dropped` 弃文 | 不看了 | **不查** | **不进** |

**外部只有两个维度**：`favorites`（是否收藏/喜欢）与 `tracking`（4 个互斥状态）。
`favorites` 是**独立的正交维度**——「收藏了并且看完了」是常见组合，
收藏决定「学不学画像」。

## 二、状态转换表（穷举）

| 当前 → 目标 | 收藏 | tracking | 说明 |
|---|---|---|---|
| （无）→ want | 不变（仍为空） | want | **「＋ 加入书架」**：能读了，但**这不是收藏** |
| want → reading | 不变 | reading | 打开阅读页即自动转 reading |
| want/reading → finished | **不变** | finished | 读完不该丢掉收藏 |
| want/reading → dropped | **清除** | dropped | ⚠ 用户明确要求：弃文就自动移出收藏和在读 |
| finished → reading | 不变 | reading | 重看 |
| dropped → reading | 不变 | reading | 重新捡起来 |
| 任意 → want | 不变 | want | 移除书架（回书库） |
| 收藏开关 | 切换 | **不变** | 正交互不影响 |

### ⚠ 修正：`tracking` 没有值时 `read_tracking()` 必须返回 `None`，不许返回 `"want"`

用户原话：**「我加入书架不等于收藏，因为我（不加）看不了」** ——
他加进来只是为了能读，不代表他喜欢。两条轴绝不能混，也不能"读着读着就被加进书架"。

* 旧实现把「没有 tracking」和「想读」当成同一个值 `"want"`，于是
  「打开阅读页 → want 自动转 reading」这条规则对**已移出书架**的书也生效：
  用户点「✕ 移出」→ 打开书接着读 → 又被写回 reading → 书回到书架。
  `server.log` 里他连点三次 `off=True` 都"没反应"，就是这个。
* 同时暴露的第二个坑：`/api/add` 只建目录、**不写 tracking**，
  于是"加进来了、书架上却没有"（`on_shelf` 为假）—— 用户只能靠按 ★收藏/▸在读
  才让它出现，而详情页的 ★收藏 当时又是坏的。
  现在 `/api/add` 会显式 `ensure_on_shelf()`：写 `want` 上架，**绝不碰 favorites**。
* `shelf_source_ids()`（推荐卡/书库卡显示"✓ 已在书架"用的）也改成同一套判定，
  否则会出现"卡片说已在书架、点进书架却没有、也没法加回来"。

**关键修正（本次）**：原先 `favorites` 与 `finished/dropped` 耦合在
`book_status()` 的优先级里，导致「收藏+看完」只显示收藏、看不出看完。
现在**两者独立存储、独立显示**：卡片上「收藏」和「看完」是两个徽标，可以同时出现。

## 三、UI 显示必须等于实际状态（用户要求）

规则：**按钮的 `on` 状态直接由服务端数据决定，不用本地猜测**。

```
收藏按钮 on  ⇔  favorites 为真
在读按钮 on  ⇔  tracking == reading
看完按钮 on  ⇔  tracking == finished
弃文按钮 on  ⇔  tracking == dropped
```

徽标同理，最多两个（收藏 + 一个 tracking）。

## 四、交互细节（这些以前都踩过）

| 细节 | 做法 | 为什么 |
|---|---|---|
| 点击后立刻有反馈 | 先本地改按钮/徽标，再发请求；失败则回滚并提示 | 等 900ms 才刷新，用户以为没反应 |
| 按钮不能长时间 `disabled` | 请求期间禁用，**返回后立刻恢复** | `disabled` 的按钮不触发 click（MDN） |
| 失败必须可见 | 显示「⚠ 保存失败」并回滚 | 静默失败 = 用户以为点了没用 |
| 刷新要绕过缓存 | 响应一律 `Cache-Control: no-store` | 生成页面是动态的，缓存会给出旧状态 |
| 保留当前标签页 | hash 路由，刷新后停在原 tab | 否则每次操作都跳回推荐页 |
| 不需要整页刷新 | 服务端返回新状态，前端只改这一张卡 | 更快、不闪、不丢滚动位置 |
| 按钮要 `type="button"` | 一律加 | 避免在表单里意外 submit |
| **一处异常 = 一批按钮全废** | `getElementById(...).onclick=` 一律先判空 | 脚本里一个未捕获异常会掐掉它之后的所有绑定 |

### ⚠ 按钮绑定：只用**事件委托**（`ACTION_JS`），不许再逐个 `.onclick=`

这条路踩了三次「按钮按了没反应」，每次漏绑方式都不同：

1. 详情页 ★收藏 的 class 被写死成 `on` → 前端永远发 `value:false` → 收藏开不了；
2. 卡片上「更新了 +N 话 · 点我翻译」**不在 `.ctrls` 里** → 从来没人给它绑 handler；
3. 一条 `getElementById(...).onclick` 抛异常 → 它之后的绑定全部失效。

现在全站只有一个绑定点：`document.addEventListener('click', ...)`，
匹配 `[data-act] [data-d-act] [data-add] [data-d-add] [data-want] [data-gopage]`。
按钮放在哪、是不是动态插进来的、以后新加什么按钮，都自动可用。
`test_click.py` 会按 HTML 里每个按钮**真的点一次**，断言"发出去的请求"和
"按钮状态 vs 接口状态"都对。

## 五、一致性校验（自动检查，不靠人眼）

* `test_click.py`：把页面内联脚本在最小 DOM 里**真的执行**，再按按钮属性
  **真的点一次**，断言请求正确 + `on` 状态 == `/api/library` 的真实状态。
  （只编译 JS 查不出这类 bug：语法合法、行为错。）
* `test_ui.py`：编译内联 JS + 断言委托覆盖全部动作前缀 + 不再逐个绑 `.ctrls button`。
* `test_reader.py`：章节落地章 / 空洞 / 已译章节列表 / 已译数字 / 自动补章，
  服务端函数层 + HTTP 层各测一遍。

## 四点五、阅读页的"章节"语义（用户 2026-10 报的三个 bug）

用户原话：「我还没开始看，怎么就第二话了，我第一话呢？」「自动翻译完成某章后
怎么不刷新，我还要手动刷新？」「你应该学习章节划分，你汉化完了显示汉化章节，
我点进去来看，这样清晰明了啊。」

根因（三个各自独立）：

| 现象 | 根因 | 现在的规则 |
|---|---|---|
| 一进来就是第 2 章 | `page_reader` 的 start 章没译文时会**向后找第一个有译文的章** | 只取**连续**已译章；落地章缺译 → 渲染 `#need-N` 占位块，并置 `window.__NEED__` |
| 第 1 章永远没人翻 | `next_targets(after=1)` 把"当前章之后的"排在前面，第 1 章被 want 挤掉 | `after` 本身缺译时它排**第一个**（`[after] + later + earlier`） |
| 译好一章要手动刷新 | `tick()` 只由"滚到底"触发；`poll()` 只往后**追加**，落地章译好没人管 | 有 `need` 就一进页面开始翻；循环里先 `fillNeed()`（`/api/chapter` 就地替换），再 `/api/next` 追加 |
| 目录只有本页 3 章、还是日文 | `toc` 只用 `shown` 渲染、标题取 `zh_titles`（自动翻译从不写它） | 目录列**全部已译章**（本页走锚点、本页外走 `?from=N`）；worker 翻译正文前先 `ensure_zh_titles()` 把书名+章节名翻成中文 |
| 「已译 0/23」而下面列着 6 章 | 显示用的是 `translated_count()`（从第 1 章起的**连续前缀**） | 显示一律 `have_count()` = **真有译文**的章数；`translated_count` 只留给"下一页从哪取"这类逻辑 |
| 从第 3 章直接跳到第 5 章 | `/api/next` 遇到空洞会 `c += 1` 跳过 | 不跳空洞：返回空 `html` + `need=N`，前端继续等这一章 |

末章还有一个**历史数据**问题：抓正文的旧 fallback 会把网站页脚（注册引导、
応援コメント、阅读器设置面板）当正文抓进来，LLM 又把它翻成中文，于是每章末尾
都有「点击滚动 / 部分安卓设备上字体设置不会生效」。抓取已改成只取
`widget-episodeBody` 那个 div；已落盘的脏数据用 `repair_chrome.py` 清
（先重新抓干净原文求共同前缀，再中日**同索引**一起删，对不上就跳过不猜）。

## 五点五、接口的 GET/POST 必须两边都注册（审阅发现的一类死按钮）

踩过三处，症状都是"按钮点了没反应"、而服务端日志里**什么都没发生**：

| 接口 | 原来 | 现在 |
|---|---|---|
| `/api/detail`（重抓简介/目录） | 只注册在 do_GET 里，还误用了 do_POST 作用域的 `d`（GET 直接 NameError） | 抽成 `refresh_work_detail()`，GET 读 query、POST 带 force |
| `/api/batchstate`（列表页补标题的轮询） | 只注册在 do_POST，前端用 GET 轮询 → 404 静默失败 | GET/POST 都能打（同一份只读实现） |
| `/api/status`（移出书架） | 响应没有 `removed` 字段，前端拿不到"已移出" | 回传 `removed` |

规律：**只读的东西两种方法都要能打**（GET 用于检查/轮询，POST 用于提交），
`do_GET` 和 `do_POST` 里各写一份实现的，必然漂移 —— 抽成同一个函数。

## 六、补充：`on_shelf`（「不在书架上」也是合法状态）

**踩过的 bug**：移除「在看」和「收藏」后，书还在书架里。

原因是最初只有 4 个状态，而**移除只是退回 `want`**——但 `want` 也是一个分组，
所以书删不掉。而且当时的"兜底把漏掉的书放回新分组"把问题藏住了。

修正后的模型：

```
on_shelf = bool(favorites) or tracking in {want, reading, finished, dropped}
```

* 书架**先按 `on_shelf` 过滤**，再按 tracking 分组
* 「移出书架」= 清空 `tracking` 与 `favorites`，**不是**退回 `want`
* 译文保留，随时可加回（不做单向删除）
* **禁止**写"把漏分组的书兜回某个分组"的兜底
* `shelf_source_ids()`（推荐卡/书库卡上那句「✓ 已在书架」）**必须用同一个判定**，
  否则会出现"卡片说已在书架、书架里却没有、而且没按钮加回来"

| 意图 | 入口 | 结果 |
|---|---|---|
| 移出书架 | `action=off` | tracking=None, favorites=None → 不在书架 |
| 重新加入 | `action=favorite` 或 `/api/add` | on_shelf=True（收藏堆 / 想读堆） |
| 恢复进行中 | `action=reading` | tracking=reading |

**旧数据迁移只跑一次**（`.shelf-migrated` 标记）：有进度但无书架标记的书
标为在读，否则老用户的书会全部消失；但若重复跑，用户主动移出的书会被
反复自动加回书架。
